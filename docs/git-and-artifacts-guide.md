# Git And Artifacts Guide

このドキュメントは、Git 運用と生成物の扱い方をまとめたものです。  
このプロジェクトでは、コード本体より「生成物と依存バイナリ」で事故りやすいので、最初に読んでください。

## 1. まず結論

基本方針は次です。

- ソースコードをコミットする
- 生成物はできるだけコミットしない
- 依存バイナリは必要性を確認してから扱う

## 2. 競合しやすいもの

特に競合しやすいのは以下です。

- `.cso`
- `.lib`
- `.pdb`
- `.exe`
- `foundation.log`
- `imgui.ini`

理由:

- バイナリなので GitHub 上で差分が見えない
- 自動マージできない
- 人によって中身が変わりやすい

## 3. できるだけコミットしないもの

原則として、以下はコミットしない方が安全です。

- `build/`
- `*.pdb`
- `*.exe`
- `foundation.log`
- `imgui.ini`
- ビルドで自動生成される `.cso`

## 4. 例外的に扱うもの

### `dxlib_support_libs/`

このプロジェクトは現状、`dxlib_support_libs/` が無いとリンクエラーになります。  
そのため、今は実用上このフォルダが必要です。

ただし、これも本来は「なるべく毎回差分を出したくない」種類のファイルです。  
更新するときは次を確認してください。

- 本当に必要な更新か
- 全員のビルドを助ける変更か
- 単なるローカル復旧ではないか

## 5. `.cso` の扱い

`.cso` はシェーダのコンパイル済みバイナリです。  
これがブランチ間で競合すると、ほぼ人力解決になります。

実際の対処方針:

- 可能なら Git 管理から外す
- 置くなら「誰が更新したか」を共有する
- 競合したら `ours/theirs` のどちらかを採る

## 6. マージ時に起こりやすいこと

### `modify/delete` 競合

例:

- 片方のブランチで `.cso` を更新
- もう片方で `.cso` を削除

このとき GitHub 上で

- `This branch has conflicts that must be resolved`

になりやすいです。

### 対処

1. どちらを採るか決める
2. コマンドラインで解消する
3. merge commit を切る
4. push する

## 7. コミット前チェック

コミット前に最低限これを見ます。

- `git status --short`
- `git diff --stat`

確認ポイント:

- `foundation.log` が混ざっていないか
- `build/` が混ざっていないか
- 意図しない `.cso` が入っていないか
- `dxlib_support_libs` を本当に含めるのか

## 8. push 前チェック

push 前に見るもの:

- ビルドが通るか
- 関係ない生成物を含んでいないか
- 競合しやすいファイルを不用意に更新していないか

## 9. チーム内で共有した方がいい変更

以下は push 前に共有した方がよいです。

- `DirectXFoundation.vcxproj` の変更
- `dxlib_support_libs/` の変更
- `.cso` の追加・削除
- `.gitignore` の変更

## 10. 事故を減らす運用

おすすめは次です。

- 生成物をなるべく PR に入れない
- ビルド不能を避けるための依存復旧だけは別で扱う
- 1 PR 1 目的にする
- merge 前に `master` を取り込む

## 11. 困ったとき

迷ったら次の順で判断してください。

1. それはソースコードか
2. それは再生成可能か
3. チーム全員に必要か

この 3 つで

- `No`

が多いなら、基本はコミットしない方が安全です。
